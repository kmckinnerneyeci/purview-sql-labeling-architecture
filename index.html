Executive overview

The proposed solution connects three distinct capabilities: Purview Data Map identifies and classifies SQL column assets; an integration adapter reuses the customer’s approved compliance sensitivity-label policy as its mapping source; and a controlled SQL process applies eligible labels to the matching live columns.

Microsoft capability

Discover and classify

Purview supports scanning on-premises SQL Server through a self-hosted integration runtime and can attach classifications to column assets in the catalog.

Custom integration

Bridge policy to SQL

A custom service retrieves catalog classifications, reads approved compliance policy and label configuration, resolves the source column, applies safeguards, and issues SQL changes.

Operational control

Preserve and prove

Every column decision is recorded. Existing labels are never lowered; writes are rechecked, verified, and reconciled against current database metadata.

Positioning This is not an out-of-the-box Purview synchronization feature. The solution combines documented scanning, catalog APIs, compliance administration tooling, and SQL metadata commands. The policy export and classifier equivalence must pass a proof of concept before production design is finalized.

Proposed processing workflow

Scan and wait for catalog readiness

Run a scheduled or triggered Purview scan for an agreed database scope. Continue only after the run succeeds and the expected column assets and classifications are available.

Export and validate policy inputs

Use supported compliance administration interfaces to retrieve the relevant auto-label policy, rules, and tenant label inventory. Snapshot the configuration and version it for audit. Validate whether each rule condition has a safe equivalent in Data Map classification output.

Enumerate classifications and resolve targets

Retrieve column entities and classifications through the Data Map API. Resolve each catalog asset to one exact live server, database, schema, table, and column. Skip stale, ambiguous, or unmatched assets.

Evaluate and generate decisions

Apply only validated policy translations. Choose the highest applicable approved label for multiple detections. Compare the proposed label against the SQL column’s current metadata using an explicit GUID-based priority map.

Apply safely and verify

Re-read the target metadata immediately before any write. Apply only absent-label or approved-upgrade cases, then read back the SQL catalog view to verify the resulting label, identifier, information type, and rank.

Audit, report, and reconcile

Record every evaluated column and outcome. Publish run, coverage, change, and exception reports. Periodically compare current SQL metadata with automation history to identify external changes.

Metadata preservation SQL Server permits one sensitivity classification per column, and adding a classification replaces the existing classification. The writer must therefore construct the complete approved resulting state, preserving information-type and rank values unless an approved policy explicitly changes them.

Customer inputs and dependencies

Platform and access

  • SQL Server versions, editions, topology, and deployment environment.
  • Purview account, collection layout, Data Map roles, API permissions, and scanning scope.
  • Self-hosted integration runtime ownership, capacity, high availability, maintenance, and network route.
  • SQL scan identity and separate automation identity with only the required classification permission.
  • Key Vault, secret rotation, TLS, DNS, proxy, firewall, and monitoring arrangements.

Policy and operations

  • Applicable compliance policy/rule names, supported export method, and responsible policy owner.
  • Authoritative sensitivity label names and GUIDs, plus approved priority ordering.
  • Approved equivalence between Data Map classification names and compliance rule conditions.
  • Scan cadence, latency tolerance, database scope, expected change rate, and maintenance windows.
  • Audit repository, reporting platform, retention, access, alerting, and support ownership.

Important caveats and design decisions

Policy reuse does not mean the compliance service evaluates SQL column assets

The compliance auto-label policy is treated as a policy source. Data Map classifications must be explicitly compared with the conditions exposed by the relevant compliance rules. Similar-looking classifier names are not sufficient proof of equivalent detection semantics.

Policy retrieval needs a supported and stable integration contract

Security & Compliance PowerShell documents retrieval cmdlets for labels, policies, and rules. Before automating, inspect whether the returned rule properties expose the exact classifier, scope, exceptions, and target label needed. Do not rely on undocumented service endpoints or silently interpret unsupported rules.

SQL Server compatibility determines the write path

The documented ADD SENSITIVITY CLASSIFICATION statement applies to SQL Server 2019 and later. Earlier versions require a separate compatibility assessment. The relevant SQL permission is ALTER ANY SENSITIVITY CLASSIFICATION.

Scanning and source labeling are separate processes

Purview Data Map scan results do not automatically write SQL Server classification metadata. The integration performs the source update and validates the result.

Classification is sample-based, not a full-table guarantee

Microsoft documents that for tabular data sources such as SQL, Data Map samples the top 128 rows for classification—not every row in the table. Sensitive values outside the sampled rows can therefore be missed. A SQL table has no guaranteed row order unless one is explicitly defined, so “top 128” should not be interpreted as a stable set of physical rows. Validate the scanner's observed behavior for the configured SQL source in the proof of concept. Where broader coverage is required, agree on complementary controls such as full-data SQL checks.

Audit coverage requires more than application logs

The orchestrator can fully log its own decisions but cannot observe every external database change by itself. If a complete record of manual or other-client changes is required, assess SQL Server auditing and periodic before/after metadata snapshots.

Label display should be tested with the customer’s SSMS configuration

Verify tenant label availability, SQL metadata persistence, and display behavior against the actual SQL Server and SSMS versions in the pilot. Catalog labels and SQL column metadata are distinct states.
